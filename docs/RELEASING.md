# Releasing

One tag ships everything. Pushing `vX.Y.Z` starts two workflows:

- `release.yml` (generated by [dist](https://axodotdev.github.io/cargo-dist/))
  builds the `tether` binary for macOS and Linux, on arm64 and x86-64, and
  puts the archives, their checksums and `tether-cli-installer.sh` on a GitHub
  release.
- `pypi.yml` builds `sdks/python` and publishes it to PyPI as `tether-agents`.

`tetherd` is not shipped as a binary of its own. The `tether` binary carries
the daemon as `tether daemon`, and the Python SDK starts it that way when no
`tetherd` is on `PATH`.

## Steps

1. Set the version in two places, to the same value: `version` under
   `[workspace.package]` in `Cargo.toml`, and `version` in
   `sdks/python/pyproject.toml`. Run `cargo check` so `Cargo.lock` follows.
   Each workflow refuses a tag that does not match its version.
2. Merge that to `master`.
3. Tag the merge commit and push the tag:

   ```sh
   git tag v0.3.0
   git push origin v0.3.0
   ```

4. Watch both workflows. A PyPI version cannot be published twice: if
   `pypi.yml` published and `release.yml` failed, fix it and re-run that
   workflow instead of moving the tag.

## One-time setup

- **PyPI.** Publishing uses trusted publishing, so no token is stored. On
  PyPI, add a trusted publisher for the project `tether-agents` (a pending
  publisher, before the first release): this repository, workflow `pypi.yml`,
  environment `pypi`.
- **GitHub.** Create an environment named `pypi` in the repository settings.
  Adding a required reviewer to it makes each publish wait for approval.

## Changing the release build

`release.yml` is generated. Edit `dist-workspace.toml` and run
`dist generate`; a hand edit makes the workflow's own check fail. To see what
a release would contain without building it, run `dist plan`.

There is no Windows build: the daemon listens on a Unix socket and the
process sandbox uses Unix process groups and rlimits.
